## Log

- Four PRs merged into main between the two tags: PR #50 (`7f5a845`) rewrites the six legacy `test/` scripts as `package:flutter_test` suites, PR #49 (`7b4213e`) records v0.4.23, PR #47 (`6567b8d`) records where the CI coverage actually is and checks the workflow patches in as `docs/patches/`, and PR #51 (`0ab3263`) is the only one that changes what the app does.
- The bug was reported as "when I type, the text is not visible, the bottom menu covers it". Root cause: the canvas is an `InteractiveViewer` clipped to a box, the scaffold shrinks it by the keyboard inset, and nothing moved `transformationController` when the bottom of that box disappeared — so the line being written stayed where it had been, under the menu. The fix reads the caret from the live `RenderEditable` in the clipped canvas's own coordinates and shifts the transform until the caret, or the top of its line, is `_caretKeepIn` inside the clip; it runs after the keystroke and after any metrics change, because a keyboard appearing over an already-written line is the same bug with a different trigger.
- Reading the caret off `RenderEditable` rather than the app's own layout was forced by measurement: the first implementation used `_layoutDocument()`'s line geometry and under-shot (caret at 592 with the clip floor at 376). The document `TextField` merges the theme `bodyLarge` (`height: 1.5`) and paints 30 px lines for its fontSize 20, while `_layoutDocument()` measures 20 px.
- That divergence is still in the code and is deliberately not fixed here. It also affects tap-to-caret placement (`_pointHitsDocumentLine`, `getPositionForOffset`) and `_growPagesForDocument`, both of which work in the 20 px model while the field paints 30 px lines. Fixing it changes page breaks and tap targets and needs its own tests.
- PR #51's four tests were each watched failing first: a line typed under the keyboard left the visible band at 828 against a floor of 376; a keyboard opening over a visible line moved it 182 px past the floor; the "does not jump" guard was proven by mutating the shift and watching it fail; a canvas shorter than one line shook the page with block tops at `[-72, -14, 44]` before the bottom edge was made to win.
- Merging was serial again, and `PUT /pulls/N/merge` answered **502 Server Error** on PR #50 while the commit actually landed. A 5xx from that endpoint says nothing about the result, so the driver now re-reads `GET /pulls/N` before retrying instead of treating it as a failure.
- The machine rebooted mid-run and `/tmp` is a tmpfs mount, which deleted eleven worktrees and every log at once. Nothing was lost because each branch was already pushed, but `git worktree prune` was needed before the branches could be checked out again. Everything from here on lives under the session directory.
- Two environment faults had to be repaired before an Android build could run locally at all: `android/local.properties` said `sdk.dir=/home/peti`, which made Gradle die with "NDK is not installed" after 17 minutes even though the pinned `ndk/28.2.13676358` is installed, and Java is not on `PATH` by default here. With `flutter config --android-sdk ~/android-sdk` and `JAVA_HOME=~/tools/jdk-17.0.21+9` a debug APK builds in about 30-90 s.

## Don't repeat

- Do not read a 5xx from the merge endpoint as "the merge failed", and do not retry it blind: re-read the PR first. Half of the confusion in this release cycle came from a 502 that had already merged.
- Do not keep worktrees, logs or driver scripts under `/tmp` on this machine. It is tmpfs; a reboot deletes them and a background command's exit code then means nothing because the log it wrote is gone.
- Do not trust the generated `android/local.properties`: it can hold a parent-directory SDK path, which fails as "NDK is not installed" rather than "SDK not found", and burns twenty minutes of Gradle before it says so.
- `mergeable` comes back `null` right after a merge because GitHub computes it lazily; re-poll rather than reading it as a conflict.
- Windows and Linux desktop artifacts are produced by the release workflow only. This machine has no Windows toolchain and no GTK/clang/cmake on `PATH`, so a local `flutter build windows` or `flutter build linux` is not available as a gate.
