# Publish Pennino v0.4.26

- Goal: ship the card that follows the note rather than the pin button, and
  publish the binaries.
- Owner: Qoder.
- State: release published from `57742f7`; assets verified from their
  downloaded bytes (see Proof below).

## Log

- One behaviour change separates this tag from `v0.4.25`: PR #59 (`d6d244f`)
  makes the home-screen preview follow a successful autosave instead of waiting
  for someone to press "Update home widget". PR #60 (`57742f7`) is the version
  bump and nothing else. The design, the nine tests and their mutation proofs
  are in
  [widget-refreshes-on-save](./2026-11-14-widget-refreshes-on-save.md); this
  note records the release.
- The release goes out over the same seam as the last two, because branch
  protection needs a commit that CI already accepted on all three jobs: bump PR
  green on its own head, merge, post-merge main green, and only then an
  annotated tag at exactly that commit - the workflow that signs binaries fires
  on a tag and on nothing else.
- What a phone user is told about this release, measured rather than assumed.
  The GitHub release body is `## What's Changed` with the three merged PRs and
  a `v0.4.25...v0.4.26` compare link - the tag workflow's generated notes, and
  nothing else; the same shape as `v0.4.24` and `v0.4.25`. It does not contain
  `fastlane/metadata/android/en-US/changelogs/30.txt`, and grepping the repo
  shows no code path that reads that file either: `fastlane/` holds only
  `metadata` with no `Fastfile`, and no workflow mentions fastlane. So the
  changelog text is store-facing copy for whoever publishes to a store, while
  the behaviour itself reaches the device in the APK.
- `PUT /pulls/60/merge` was first attempted with `POST` and answered `404 Not
  Found`. A wrong verb on that route is a 404 rather than a 405, and it writes
  nothing: a fresh `GET /pulls/60` showed the PR still `open`, `mergeable=True`,
  `mergeable_state=clean`, and the same call with `PUT` merged it. The error
  text was not read as a statement about the PR.
- `flutter build apk --release` refuses on this machine again, quoted verbatim
  in PR #60: "android/key.properties is missing, so release builds cannot be
  signed. Refusing to fall back to the debug signing config: a debug-signed
  release APK cannot be installed over previous releases." That is the designed
  behaviour, and the reason the signed artifacts come only from this workflow.

## Don't repeat

- Do not trust the verb in a hand-rolled GitHub call. `POST /pulls/N/merge` is
  a 404 that leaves the PR open; the endpoint is `PUT`, and the only safe
  reading of that 404 is a fresh `GET /pulls/N`.
- Do not report main as green from a background wrapper's exit code. When the
  watcher had produced no verdict line the run was still `in_progress` on two
  jobs; the `MAIN GREEN …` line in the log is the evidence, and nothing else.
- An artifact the same length as its predecessor proves nothing by itself -
  `v0.4.24`, `v0.4.25` and `v0.4.26` are all 53,465,281 B with the same
  6,095,752 B arm64 snapshot, and only their digests differ. Ask for a string
  literal only this release can contain inside `libapp.so`, and check
  ancestry.
